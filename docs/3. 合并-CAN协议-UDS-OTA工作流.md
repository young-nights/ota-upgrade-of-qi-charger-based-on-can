# Qi 无线充电模块 — CAN 协议 · UDS · OTA 工作流

> **架构前提（OTA-ARCH-0920）**：架构为
> **Boot(16KB) + App 区(48KB) + 备份区(48KB)** 的单 App 升级流：
> 主机通过 APP 的 UDS 把新固件写进**备份区**，APP 校验通过后置 `backup_valid` 标志并自复位，
> **BOOT 在复位后把备份区搬运到 App 区**（擦 App 区 → 复制 → 复核 → 清标志 → 跳转）。
>

# 一、CAN 通信基础

## 1. 网络拓扑

CCU（地址 0x03）是诊断主节点，MCU（地址 0x0D）是诊断目标节点。MCU 再通过 UART2 转发给 Qi 充电芯片。

```
CCU (0x03)  ──── CAN 总线 ────  MCU (0x0D)  ──── UART2 ────  Qi 芯片
  诊断主节点                        诊断目标节点                Qi 充电芯片
```

## 2. 物理层参数

| 参数 | 值 | 出处 |
|------|-----|------|
| CAN 标准 | CAN 2.0B，Classical CAN | can_driver.h（文件头） |
| 波特率 | 250 kbps | can_driver.c:43-46 |
| 帧格式 | 29 位扩展帧 | can_driver.c can_driver_init 注释 |
| 最大 DLC | 8 字节 | can_driver.h `CAN_DRIVER_MAX_DATA_LEN=8` |
| 引脚 | PA11=CAN_RX / PA12=CAN_TX（AF4） | can_driver.c can_driver_init |

**位时序**（can_driver.c:37-46）：CAN 时钟 18 MHz（APB1 180 MHz ÷ 10），
`DIV=10，BTS1=54，BTS2=18` → 18 MHz ÷ (54+18) = 250 kbps，采样点 54/72 = 75%。

**接收过滤**：硬件过滤器接收全部扩展帧；协议层只认两种 ID
（can_protocol.c:1886-1890 `can_protocol_rx_handler`）：

- 物理寻址请求 `0x18DA0D03`；
- 功能寻址广播，按掩码匹配 `(id & 0x1FFFFF00) == 0x18DB3300`，即整个 `0x18DB33xx` 组都收
  （ISO-TP 层同样过滤，isotp.c:282）。

## 3. CAN ID 一览

| CAN ID | 方向 | 用途 | 出处 |
|--------|------|------|------|
| `0x18DA0D03` | CCU → MCU | UDS 物理寻址请求 | can_driver.h `CAN_ID_UDS_REQUEST`；can_protocol.h `CAN_PROTO_UDS_REQUEST` |
| `0x18DA030D` | MCU → CCU | UDS 物理寻址响应 | can_driver.h `CAN_ID_UDS_RESPONSE` |
| `0x18DB33F1` | CCU → 所有外设 | UDS 功能寻址广播（PF=0xDB，PS=0x33；APP 实际按 `0x18DB33xx` 组接收） | can_driver.h `CAN_ID_FUNCTIONAL_REQUEST`；can_protocol.c:1889 |
| `0x18FF260D` | MCU → 总线 | 生命周期状态广播（APP 事件帧 + Boot safe mode 心跳） | can_driver.h `CAN_ID_LIFECYCLE_BROADCAST` |
| `0x18FF480D` | Boot → 总线 | Boot 开机决策链诊断帧 M1~M4（仅观察，不影响决策） | boot_safe_mode.h `BOOT_DIAG_CAN_ID` |

## 4. SIT1145 收发器状态机

CAN 收发器 SIT1145 通过 SPI1（PA4=CS / PA5=SCK / PA6=MISO / PA7=MOSI）控制，两种工作状态：

| 状态 | 行为 |
|------|------|
| Normal（0x07） | 正常收发。APP/Boot 在需要 CAN 时调 `sit1145_normal_mode_set()` 切入 |
| Standby（0x04） | 低功耗监听。收发器自己监听总线，任意 250kbps 扩展帧触发 WUP 引脚唤醒 MCU |

**当前固件编译开关：`CAN_LP_STANDBY_ENABLE = 1`（can_protocol.h；未定义也按启用处理）**：

- **上电/跳转进入 App 后收发器即 Normal、立即可通信**；
  `sit1145_init` 无停机步骤，收发器留步骤7 CMC 配置态；
  `can_protocol_init` 统一置 `g_lp_need_online=1`，首次 `can_protocol_poll` 调
  `can_lp_enter_normal()` → `sit1145_normal_mode_set()` + `can_driver_online()`；
- **空闲 30 秒（UDS 无收发）进 Standby**（`CAN_LP_IDLE_TIMEOUT_MS = 30*1000`，can_protocol.c）；
  空闲比较为有符号 `(int32_t)(now-g_uds_last_ms)`，消除 uint32 下溢误判；
  进睡前打 SB（StandBy，进待机标记）`06 41 53 42`；
- 唤醒链路：收发器检出总线帧置 WUP → `sit1145_wakeup_pending()` → 引脚回 AF →
  `sit1145_normal_mode_set()`（重试 3 次）→ 清 CW 等 RXD 恢复隐性 → CAN1 重新 online →
  30ms RX harvest（抢在主机控制器重发窗口内 ACK）→ 100ms 后发 BOOTUP 标识帧
  （`01 41 57 4B …`，can_protocol.c `can_lp_enter_normal`）；
- `can_lp_hold_standby` 失败 tick 自旋 1ms 重试一次；两次失败置 sticky
  `g_lp_standby_fail`，挂 DID `0x2119` flags **bit2**；
- OTA 相关状态（下载中 / backup_valid 置位 / 上次搬运失败）上电强制 CAN 在线，
  不进 Standby（`can_lp_trial_needs_normal`，can_protocol.c）。
  不存在「上电即 Standby」模式，也无对应开关。

Boot safe mode 主循环每 500ms 重切一次 SIT1145 Normal，防止收发器掉电后诊断帧发不出去
（boot_safe_mode.c enter_safe_mode）。

# 二、UDS 服务列表

## 5. 服务总表

APP 侧完整 UDS 实现在 `can_protocol.c`（分发函数 `uds_process_message`）+ `ota_download.c`。
Boot 常规路径**不做 UDS**（验签后直接跳转）；Boot Safe Mode 只有最小应答（见 §20）。

| SID | 服务 | APP 行为 | 门禁（会话 + 安全） |
|-----|------|---------|---------------------|
| 0x10 | DiagnosticSessionControl 会话控制 | 支持 0x01 默认 / 0x02 编程 / 0x03 扩展；进 Programming 时顺手关无线充 5V（`board_5v_set(0)`） | 无 |
| 0x11 | ECUReset 复位 | **不支持**：请求落入派发默认分支回 NRC serviceNotSupported，不产生复位。升级完成后的复位由 `0x37` 收尾自动执行 | 无 |
| 0x22 | ReadDataByIdentifier 读 DID | 支持单帧多 DID 连读；无效 DID → NRC 0x31；响应超 256B 缓冲 → NRC 0x14 | 无（只读） |
| 0x2E | WriteDataByIdentifier 写 DID | 逐 DID 门禁，见 [§25 门禁表](#25-写-did02e门禁表) | 依 DID 而定 |
| 0x27 | SecurityAccess 安全访问 | ECDSA P-256 Seed & Key，详见 [§8](#8-安全访问seed--key) | 本身即解锁操作 |
| 0x31 | RoutineControl 例程控制 | `31 01 FF00` 擦**备份区**（0x08010000~0x0801BFFF），转发 `ota_dl_handle_erase` | Programming + 已解锁 |
| 0x34 | RequestDownload 请求下载 | **地址门禁：仅接受 0x08010000**（≠ 备份区基址回 NRC 0x31）；响应 `74 20 01 00`（每块最大 256B） | Programming + 已解锁 + 已擦除 |
| 0x36 | TransferData 数据传输 | 流式写入备份区（XATO 镜像）；blockSeq 从 0x01 起递增，0xFF 后回绕 0x01 | Programming + 已解锁 + 0x34 已完成 |
| 0x37 | RequestTransferExit 传输退出 | 字节数核对 → 镜像校验 → `commit_backup` 提交 → 回 `77` → **自复位** | Programming（+ 解锁，见 §6） |
| 0x38 | TransferSignature | **未实现**，回 NRC 0x11（签名在 XATO 镜像头里，随 0x37 一起校验） | — |
| 0x3E | TesterPresent 保活 | 非 suppress 回 `7E <sub>`；suppress（sub bit7=1）不回但同样刷新 S3 | 无 |

分发出处：can_protocol.c `uds_process_message`（各 SID case 分支）。

## 6. 各服务详解

### 0x10 — 会话控制

| 子功能 | 值 | 说明 |
|--------|-----|------|
| Default | 0x01 | 正常运行，只读诊断 |
| Programming | 0x02 | 固件更新（OTA 全流程在此会话） |
| Extended | 0x03 | 受保护配置（充电使能/功率限值写入） |

- 正响应：`50 <会话> <P2 高> <P2 低> <P2* 高> <P2* 低>`，
  实际组帧 `50 02 00 32 01 F4` = P2 50ms（`UDS_P2_TIMEOUT_MS=50`）+ P2* 5000ms
  （`UDS_P2_STAR_TIMEOUT_MS=5000`，÷10 编码为 0x01F4；can_protocol.h:114-115，组帧在 handle_diag_session_ctrl）；
- 子功能非法（不是 0x01/0x02/0x03）→ NRC 0x12；长度不足 → NRC 0x13；
- suppress 位（bit7）置 1 不回正响应，但会话照常切换；
- 切到 Default 会中止下载并清安全状态（见 §7）。

### 0x11 — ECU 复位（不支持）

- 该服务不受支持（无 `handle_ecu_reset`，不回 `51 01`、不执行复位）；对
  `11 01` 的请求由服务派发默认分支回 NRC serviceNotSupported，
  设备不会因该请求复位。
- 升级完成后的复位由 `0x37` 收尾自动执行（`0x77` → SHUTDOWN 广播 →
  `NVIC_SystemReset`），主机不应发 `11 01`。metadata 已在
  `commit_backup` 落盘，BOOT 搬运不受影响。

### 0x22 — 读 DID

- 请求：`22 <DID_H> <DID_L> [...]`，支持一次读多个 DID；
- 正响应：`62 <DID_H> <DID_L> <数据> [...]` 顺序拼接；
- 任一 DID 无效 → 整条请求 NRC 0x31；拼接后超 256B 缓冲 → NRC 0x14；
  长度不满 3 或 DID 数不成对 → NRC 0x13（handle_read_data_by_id）。
- 每个 DID 的返回格式见 [第五章 DID 详细定义表](#五did-详细定义表)。

### 0x2E — 写 DID

逐 DID 门禁（同一 case 内**会话检查先于安全检查**：拿 NRC 0x33 说明会话还在、只是没解锁；
拿 NRC 0x22 才是会话丢了）。完整门禁与取值见 [§25](#25-写-did02e门禁表)。

### 0x27 — 安全访问

详见 [§8 安全访问](#8-安全访问seed--key)。

### 0x31 — 例程控制（擦备份区）

- 请求：`31 01 FF 00`（sub=0x01 启动，RID=0xFF00 `ROUTINE_ERASE_MEMORY`，can_protocol.h）；
  **不携带地址/长度参数**，擦除目标由固件固定为备份区；
- 门禁（ota_download.c ota_dl_handle_erase）：
  - 非 Programming → NRC 0x22；未解锁 → NRC 0x33；
  - `len < 4` → NRC 0x13；sub≠0x01 或 RID≠0xFF00 → NRC 0x31；
  - 活动区保护：目标若等于 App 区（0x08004000）→ NRC 0x22；范围越界 → NRC 0x72；
- 擦除过程：按 1KB 扇区逐个擦 0x08010000~0x0801BFFF，每扇区 IRQ 屏蔽 + flash_unlock +
  **有界轮询**（`flash_sector_erase_bounded`，预算 `OTA_ERASE_POLLS_MAX=4000000` 次 ≈ 4 倍余量），
  超时/失败 → `flash_lock` + `__enable_irq` 恢复后回 NRC 0x72；
- 长操作保护：开始先回 `7F 31 78`（ResponsePending），擦除循环中持续泵 0x78 防主机等死；
- 擦完顺手清 metadata：`backup_valid=0`（丢弃上一次中断升级的残留标志）、
  `ota_state=DOWNLOADING`（ota_download.c）；
- 正响应：`71 01 FF 00`。
- **Device Info 保留区（0x0801D000~0x0801DFFF）不在擦除范围内**，SN/公钥 OTA 后保留。

### 0x34 — 请求下载

- 请求：`34 <DataFormatID=0x00> <ALFID> <地址 addr_n 字节> <长度 size_n 字节>`，
  ALFID 高 4 位=地址字节数、低 4 位=长度字节数；
- 门禁（ota_download.c ota_dl_handle_request_download）：
  - 非 Programming → NRC 0x22；未解锁 → NRC 0x33；没先 0x31 擦除 → NRC 0x24；
  - ALFID 的 addr_n/size_n 必须各为 1~4，且报文长度够 → 否则 NRC 0x13（不存在"无地址"的简单写法）；
  - **地址值必须等于 0x08010000（备份区基址），否则 NRC 0x31** —— 单一目标写死门禁；
  - mem_size=0 或超过备份区大小 0xC000 → NRC 0x31；
- 正响应：`74 20 <maxBlock 高> <maxBlock 低>` = `74 20 01 00`，
  maxNumberOfBlockLength = `OTA_DL_MAX_BLOCK_LEN = 256`（ota_download.h:14）。

### 0x36 — 数据传输

- 请求：`36 <blockSeq> <数据...>`；blockSeq 从 0x01 开始，每包递增，0xFF 后回绕 0x01；
- 门禁（ota_download.c ota_dl_handle_transfer_data）：
  - 非 Programming → NRC 0x22；未解锁 → NRC 0x33；0x34 未完成 → NRC 0x24；
  - `len < 3` → NRC 0x13；
  - **重复包幂等**：blockSeq 等于"期望值-1"（即刚确认过的包）→ 直接重回正响应，不重复编程；
  - blockSeq 不连续 → NRC 0x73 且下载状态作废（需重新 0x34）；
  - 写入超备份区范围 → NRC 0x71；Flash 编程失败 → NRC 0x72；
- 正响应：`76 <blockSeq>`。
- 内部按 4 字节字编程（`program_words`），尾包不足 4 字节时补 0xFF 凑整字写入
  （`program_flush`，0x37 收尾时执行）。

### 0x37 — 请求传输退出（校验 + 提交 + 自复位）

- 请求：`37`（无参数）；
- 门禁与收尾（ota_download.c ota_dl_handle_transfer_exit + ota_dl_poll）：
  1. 非 Programming → NRC 0x22；
  2. 传输未激活（g_active=0）：若 `g_trial_ready`≠0（此前已提交成功、复位还没落）→ 幂等回 `77`；
     否则 → NRC 0x71；
  3. 未解锁 → NRC 0x33；
  4. 进入长操作：先回 `7F 37 78`，主循环 `ota_dl_poll` 执行收尾：
     - `program_flush` 补尾字；
     - **字节数核对**：实际写入 ≠ 0x34 申报的 size → NRC 0x72；
     - **镜像校验 `verify_backup_image`**（见 §13）→ 失败 NRC 0x72；
       （验签开关 `OTA_VERIFY_ENFORCE`/`BOOT_VERIFY_ENFORCE` **当前=0，测试期语义**：验签照常计算，失败不拒绝、强制放行并留 g_verify_bypass_hit/g_boot_verify_bypass_hit 标记；置 1 恢复严格校验）
     - **`commit_backup` 提交 metadata**（`backup_valid=1`，`backup_crc32=镜像头 CRC`，
       `ota_state=IDLE`）→ 失败 NRC 0x72；
  5. 全部通过：`g_trial_ready=1` → 回正响应 `77` → 等 TX 空闲 50ms → 发 SHUTDOWN 生命周期帧 →
     **`NVIC_SystemReset()` 自复位**；BOOT 下次上电看到 `backup_valid=1` 执行搬运（§14）。
- 校验/提交失败时 metadata 不动（`backup_valid` 不置位），搬运不会发生，设备继续跑旧固件；
- 复位后主机的 0x37 重试帧会落在**新 APP 的默认会话**上 → NRC 0x22，属预期形态，
  主机脚本不判死，由复位后版本核验闭环判定（§16）。

### 0x38 — 传输签名（未实现）

签名放在 XATO 镜像头里随固件一起下发，0x37 时统一校验，因此 APP 对 0x38 直接回 NRC 0x11
（can_protocol.c uds_process_message `UDS_SID_TRANSFER_SIGNATURE` 分支）。

### 0x3E — 测试仪在线（保活）

- `3E 00` → 回 `7E 00`；`3E 80`（suppress 位=1）→ 不回，但**同样刷新 S3 计时**；
  不带子功能 → 回单字节 `7E`（handle_tester_present）；
- 不止 0x3E：**任意诊断请求都会刷新 S3**（uds_process_message 入口统一刷新
  `last_tester_present_tick`，同时刷新 CAN 空闲计时）。

## 7. 会话管理与 S3 保活

| 会话 | 值 | 用途 | 安全状态 |
|------|-----|------|---------|
| Default | 0x01 | 正常运行、只读诊断 | — |
| Programming | 0x02 | OTA 下载全流程 | 切入需重新解锁 |
| Extended | 0x03 | 充电配置写入 | 切入需重新解锁 |

**切换规则**（can_protocol.c `session_switch` / `session_reset_to_default`）：

- 切回 Default：中止下载（`ota_dl_abort`）、清安全解锁、清 seed；
- 非默认 → 另一种非默认：清安全解锁（保留会话本身）；
- **S3 超时**：非默认会话 5 秒（`SESSION_TIMEOUT_MS=5000`，can_protocol.h）没收到任何诊断请求
  → 自动回 Default 并清安全状态。超时检查在 ISO-TP 回调和主循环两处都有
  （isotp_message_received / can_protocol_poll）；
- **注意**：切 Default 并**不**清 0x27 的失败计数（fail_count 独立于会话）。

**实操含义**：擦 Flash / 多帧传输间隙要插保活——`3E 00` 或 `3E 80` 都行，
宿主脚本现行做法是长等待期间每 3 秒发一帧 `3E 80`（3s < 5s，留 2s 余量）。

## 8. 安全访问（Seed & Key）

算法：**ECDSA P-256**，对 seed 的 SHA-256 哈希签名。APP 侧验签用**编译内置公钥**
`g_app_ecdsa_pubkey`（can_protocol.c:60-71，与 Boot boot_verify.c 内置公钥同值）；
Device Info 公钥仅用于**镜像校验**（§13/§14），不影响 0x27 解锁。

```
主机                                     APP
 │  27 01  ──────────────────────────▶   │
 │  ◀── 67 01 + 32 字节 seed ─────────   │  每次 27 01 都重新生成随机 seed
 │                                        │  （LFSR + SysTick 时间熵，
 │  主机: h = SHA256(seed)               │   generate_random_seed）
 │        sig = ECDSA_sign(私钥, h)      │  私钥路径 docs/keys/private.pem
 │                                        │
 │  27 03 分片送 64B 签名 ────────────▶   │  每帧 4 字节 × 16 帧
 │  （blockSeq 0x01~0x10）               │
 │  27 02 触发验签 ───────────────────▶   │
 │  ◀── 7F 27 78（先回等待）───────────   │  长操作保护
 │  ◀── 67 02（解锁成功）─────────────   │  uECC_verify(内置公钥,
 └────────────────────────────────────────┘   SHA256(seed), 签名)

分片帧格式:  07 27 03 <blockSeq> <sig 4 字节>
第 1 帧 blockSeq=0x01（此帧同时清空签名缓冲区，从头重收）
第 16 帧 blockSeq=0x10
```

**关键行为**（can_protocol.c handle_security_access）：

| 场景 | 行为 |
|------|------|
| 已解锁状态再发 `27 01` | 回 `67 01` + 32×`0x00`（不发新 seed；主机脚本据此跳过 SendKey） |
| `27 03` 分片序号错 | NRC 0x71，签名缓冲清零，必须从 blockSeq 0x01 重发 |
| seed 未生成就发 `27 03` / `27 02` | NRC 0x24（请求序错误；验签失败后 seed 标志已清） |
| `27 02` 单帧变体 | ISO-TP 多帧载荷 `27 02 <64B 签名>`（len≥66）可跳过分片直接验 |
| 验签失败 | NRC 0x35，失败计数 +1 |
| 连续失败 3 次 | 第 3 次直接回 NRC 0x36，并锁定 30 秒（`SECURITY_MAX_FAILURES=3`、`SECURITY_LOCKOUT_MS=30000`，can_protocol.c:62-63） |
| 锁定期内 `27 01` | NRC 0x37（requiredTimeDelayNotExpired）；锁定超时后下一次 `27 01` 清计数、正常发 seed |
| 验签成功 | 解锁、清失败计数、清 seed 标志；期间先回 `7F 27 78`（ECDSA 计算耗时） |

## 9. NRC 否定响应码

| NRC | 名称 | 本项目触发场景（出处） |
|-----|------|------------------------|
| 0x11 | serviceNotSupported | 收到 0x38（未实现）；其他未实现 SID；Boot safe mode 对 22 2113/0x3E 之外的 22 DID |
| 0x12 | subFunctionNotSupported | 0x10 子功能非 0x01/02/03；0x27 其他子功能 |
| 0x13 | incorrectMessageLengthOrInvalidFormat | 各服务长度不足；0x34 ALFID 的 addr_n/size_n 不在 1~4 |
| 0x14 | responseTooLong | 0x22 多 DID 连读拼接超 256B 缓冲 |
| 0x22 | conditionsNotCorrect | 0x31/0x34/0x36/0x37 非 Programming 会话；0x2E 写 0x2101/0x210D 非 Extended；充电故障态写 0x2101=0x01；0x2131 写时 Qi IAP 不在进行态；0x37 重试帧落在自复位后新 APP 的默认会话（预期形态） |
| 0x24 | requestSequenceError | 没擦就 0x34；没 0x34 就 0x36；0x27 序错（未要 seed 先发 03/02） |
| 0x31 | requestOutOfRange | 0x34 地址 ≠ 0x08010000 或 size 非法；0x31 sub/RID 错；0x22 DID 无效；0x2E 写不可写 DID / 取值超范围；0x2120 写 data[3]≠0x04 |
| 0x33 | securityAccessDenied | 未解锁就擦/下载/写受保护 DID |
| 0x35 | invalidKey | ECDSA 验签失败 |
| 0x36 | exceededNumberOfAttempts | 0x27 连续失败 3 次（当次即回） |
| 0x37 | requiredTimeDelayNotExpired | 30 秒锁定期内发 `27 01` |
| 0x71 | transferDataAborted / transferDataSuspended | 0x27 03 分片序号错；0x36/0x37 写入超备份区范围或传输未激活就发 0x37 |
| 0x72 | generalProgrammingFailure | Flash 擦写失败/擦除有界等待超时；0x37 字节数不符/镜像校验失败/commit 失败；Qi IAP ACK 失败/超时 |
| 0x73 | wrongBlockSequenceCounter | 0x36 blockSeq 不连续 |
| 0x78 | responsePending | 长操作占线提示：0x31 擦除、0x27 02 验签、0x37 校验提交，先回 78 再出最终结果 |

NRC 常量定义：can_protocol.h `UDS_NRC_*`；0x78 应答由 `proto_send_pending` 直接以
ISO-TP 单帧 `03 7F <SID> 78` 发出（不走可能阻塞的 ISO-TP 栈）。

# 三、OTA 升级工作流

## 10. 总体思路（大白话）

1. **APP 不能擦自己正在运行的 Flash**（单 Bank，擦执行区会把程序自己擦死）；
   所以新固件先写到**备份区 0x08010000**，这一步由 APP 的 UDS 服务完成；
2. APP 收完整包后自己**先验一遍**（magic/长度/CRC32/Reset 向量/ECDSA 签名），
   验过才在 metadata 里立一个 `backup_valid=1` 的旗子，然后**自己复位**；
3. 复位后 **BOOT 接管**：看到旗子 → 先验备份区 → 擦 App 区 → 把备份区搬过去 →
   再验一遍搬完的 → **确认没问题才把旗子放倒** → 跳转运行新固件；
4. 旗子只有在"搬完且复验通过"后才清除，**中途任何断电，下次上电都会从头再来一遍**，
   不会刷成半吊子变砖（Boot 区 16KB 永远不被 OTA 触碰）。

## 11. Flash 布局 / Metadata / XATO 镜像头

### Flash 布局（boot_metadata.h / ota_trigger.h）

| 区域 | 起始 | 大小 | 说明 |
|------|------|------|------|
| Bootloader | `0x08000000` | 16 KB（0x4000） | 引导 + 搬运 + Safe Mode，OTA 不触碰 |
| App 区 | `0x08004000` | 48 KB（0xC000） | XATO 头 256B + 代码，入口 `0x08004100` |
| 备份区 | `0x08010000` | 48 KB（0xC000） | OTA 暂存区（0x34/0x36 写入目标，BOOT 搬运源） |
| Metadata 主 | `0x0801C000` | 1 KB 页 | `ota_metadata_t` 28B |
| Metadata 备 | `0x0801C800` | 1 KB 页 | 掉电安全副本 |
| Device Info | `0x0801D000` | 4 KB | SN、ECDSA 公钥、HW 版本；OTA 擦写不碰 |
| NVM | `0x0801E000` | 8 KB | APP 配置（功率限值等） |

Flash 擦除粒度：AT32F426 页大小 **1 KB（0x400）**（`FLASH_SECTOR_SIZE`/`OTA_FLASH_SECTOR_SIZE`）。

Keil 工程链接（qi_wireless_code_app.uvprojx）：`IROM(0x08004100, 0xBF00)`、
`IRAM(0x20000000, 0x5000)`；备份区**不是链接目标**，OTA 镜像就是 App 区链接的镜像
（Reset 向量天然指向 0x08004100 窗口，校验时用它挡跨槽镜像）。

### Metadata 结构（v4，28 字节，magic "MATO"）

两侧工程同源定义（boot_metadata.h / ota_trigger.h，字段偏移必须一致）：

| 偏移 | 字段 | 含义 |
|------|------|------|
| 0x00 | `magic` | `0x4F54414D` = "MATO" |
| 0x04 | `version` | `META_VERSION=4`（v3 及更早拒绝 → 默认重建） |
| 0x08 | `backup_valid` | **备份区待搬运旗子**（OTA 提交 = 置 1；BOOT 搬运复验通过 = 清 0） |
| 0x09 | `copy_fail_step` | 上次搬运失败的失败步骤码（§19） |
| 0x0A | `last_boot_reason` | 上次启动原因（§22 DID 0x2115） |
| 0x0B | `reserved0` | 对齐 |
| 0x0C | `backup_crc32` | 备份区载荷 CRC32（搬运前一致性核对用） |
| 0x10 | `copy_retry_count` | 搬运失败重试计数（DID 0x2116） |
| 0x14 | `ota_state` | 0x00 IDLE / 0x01 DOWNLOADING |
| 0x15 | `reserved[3]` | 对齐/预留 |
| 0x18 | `crc32` | 以上字段的 CRC32 |

**掉电安全**：`boot_metadata_save` **先写备份副本 0x0801C800，再写主区 0x0801C000**
（boot_metadata.c:202-211，"backup copy first so a torn primary write stays recoverable"）；
读取时主区 → 备份区 → 默认值三级回退（boot_metadata.c boot_metadata_init）。

### XATO 镜像头（256 字节，magic "XATO"）

| 偏移 | 字段 | 说明 |
|------|------|------|
| 0x00 | `magic` | `0x4F544158` = "XATO" |
| 0x04 | `image_length` | 头之后的载荷字节数 |
| 0x08 | `crc32` | 载荷 CRC32（**只算头之后的固件，不含头本身**） |
| 0x0C | `signature[64]` | ECDSA P-256 签名 R‖S（对载荷 SHA-256 签名） |
| 0x4C | `hdr_reserved_ver[16]` | 保留字段（不使用），打包固定填 0x00（版本号不在镜像头里） |
| 0x5C | `build_timestamp` | 构建时间戳 |
| 0x60 | `reserved[160]` | 预留 |

定义：ota_trigger.h `ota_image_header_t`。跳转地址 = 头所在基址 + 256
（App 区即 0x08004000 + 0x100 = `0x08004100`）。

## 12. 主机侧：UDS 庇列

OTA 脚本 `python_tools/zcanpro_ext_ota_auto.py` 实际执行的完整序列
（`run_ota`，请求 ID 0x18DA0D03，响应 ID 0x18DA030D，扩展帧 250kbps）：

```
① 探测设备        22 2113（读当前区域；safe mode 探测/唤醒收敛另见 §16）
② 进编程会话      10 02                → 50 02 00 32 01 F4（失败自动重试 8 次）
③ 安全访问        27 01                → 67 01 + 32B seed（seed 全 0 = 已解锁，跳过跳过④）
④ 签名解锁        27 03 ×16 + 27 02    → 7F 27 78 → 67 02
⑤ 固件类型        2E 2010 01           → 6E 20 10（选 APP 固件类型）
⑥ 擦备份区        31 01 FF 00          → 7F 31 78 → 71 01 FF 00
   （随后读 0x2114 应为 0x02 = 备份区标记）
⑦ 请求下载        34 00 44 + 地址 + 长度
                   地址 = 0x08010000（4 字节大端），长度 = 打包镜像总长（含 256B 头）
                   → 74 20 01 00（maxBlock = 256）
⑧ 数据传输        36 <blockSeq> <数据>，blockSeq 0x01 起，每包 128 字节
                   （脚本 TRANSFER_BLOCK_DATA=128，设备上限 254；0xFF 回绕 0x01）
⑨ 传输退出        37                   → 7F 37 78 → 77
   （脚本等待 pending 最长 45s，最多重试 5 次；设备此步校验+提交后即自复位）
⑩ 设备自复位      （0x37 收尾内自动执行）  → 无需主机请求，随后 BOOT 搬运 Backup→App
⑪ 复位后判定      三条件闭环：①APP 应答 ②0xF195 == 预期版本 ③0x2113 == 0x00
```

0x34 报文组装示例（size=0x00001000、addr=0x08010000 时）：

```
UDS 载荷: 34 00 44  08 01 00 00  00 00 10 00
          SID DF AL  地址4B大端    长度4B大端
（ALFID=0x44：地址 4 字节 + 长度 4 字节；多帧传输时按 ISO-TP FF+CF 拆分）
```

## 13. APP 侧：接收 → 校验 → 提交 → 自复位

入口：`qi_wireless_code_app/mdk_app/Src/ota_download.c`（0x31/0x34/0x36/0x37 全在这里）。

```
31 01 FF00   擦备份区 → g_base=0x08010000, g_size=0xC000, g_erased=1
34           校验地址=0x08010000/长度合法 → g_active=1, 记录 expected_size
36 ×N        按 4 字节字流式写入备份区（blockSeq 连续性检查）
37           program_flush 补尾字
             → 字节数核对（written == expected）
             → verify_backup_image()：  ① magic == "XATO"
                                        ② 0 < image_length ≤ 备份区大小-256
                                        ③ CRC32(载荷) == 头.crc32
                                        ④ Reset 向量（清 Thumb 位）落在
                                           [0x08004100, 0x08010000) 运行窗
                                        ⑤ 公钥可用（Device Info 有效公钥优先，
                                           否则回落内置公钥）
                                        ⑥ SHA256(载荷) + uECC_verify == 签名
             → commit_backup()：metadata.backup_valid=1
                                metadata.backup_crc32=头.crc32
                                metadata.ota_state=IDLE
             → 回 77 → 等 TX 空闲 → SHUTDOWN 广播 → NVIC_SystemReset
```

- 校验用公钥取值（`image_pubkey`）：Device Info 里 `pubkey_valid==0x01` 且首字节 0x04 →
  用 Device Info 公钥；否则用 APP 编译内置公钥 `g_app_ecdsa_pubkey`；两者都不可用 → 校验失败；
- SHA-256 分 256B 块计算，期间泵 `7F 37 78` 防主机超时；
- 任一步失败：回 NRC 0x72，**metadata 不提交**（旗子不立），设备继续跑旧固件，OTA 不生效；
- 成功路径的顺序刻意如此：**先让 0x77 落到总线上，再复位**（等 TX 空闲 50ms），
  主机才能确认"提交已发生"。

## 14. Boot 侧：开机决策链与搬运流程

入口：`qi_wireless_bootloader/mdk_user/Src/main.c`（决策链全文 72 行，无槽选择、无 trial 状态机）。

```
上电/复位
 ├─ ① system_clock_config（180MHz）→ NVIC GROUP4 → timer_drv_init
 │     → boot_diag_can_init（CAN 提前初始化，只为 M1~M4 能发帧）
 ├─ ② boot_metadata_init：主区→备区→默认值 三级加载（M1 诊断帧在此发出）
 │     → detect_boot_reason（复位标志快照后清零：
 │        WDG/WWDT→0x02，软件复位→0x01，POR→0x00）
 ├─ ③ backup_valid 旗子立着吗？
 │     是 → last_boot_reason=OTA_ACT(0x03)；发 M2(start)；boot_copy_backup()：
 │        1. 验备份区镜像（boot_verify_image，校验窗=App 区）
 │           失败 → copy_fail_step=失败码, retry++, reason=COPY_FAIL, 保存 → -1
 │        2. metadata.backup_crc32 与镜像头 crc32 一致性核对
 │           不一致 → copy_fail_step=0xFF, retry++, 保存 → -1
 │        3. 擦 App 区（IRQ 屏蔽+flash_unlock，1KB 扇区 × 48）
 │           失败 → copy_fail_step=0xFE, retry++, 保存 → -1
 │        4. 复制 头+载荷 备份区→App 区（字编程+回读校验）
 │           失败 → copy_fail_step=0xFD, retry++, 保存 → -1
 │        5. 复验 App 区镜像（boot_verify_image）
 │           失败 → copy_fail_step=失败码, retry++, 保存 → -1
 │        6. 提交：backup_valid=0（旗子放倒）, ota_state=IDLE,
 │           last_boot_reason=OTA_ACT, copy_fail_step=0 → 保存
 │     成功 → M2(committed)；失败 → M2(failed, fail_step)，但流程继续下一步
 │     否则 → 发 M2(no pending) 继续下一步
 ├─ ④ App 区镜像校验通过？（boot_app_image_ok）
 │     通过 → boot_jump_to_app(0x08004100)：
 │        向量合法性检查（MSP ∈ [0x20000000, 0x20005000] 且 8 字节对齐；
 │        VTOR 地址 128 字节对齐）→ 发 M4（跳转地址 LE 4B）
 │        → 关中断 → CAN1 复位+关时钟 → SPI1 关闭+关时钟 → SysTick 停
 │        → 清 NVIC → CONTROL=0 → VTOR=0x08004100
 │        → __set_MSP + 调用向量表 Reset_Handler（boot_jump.c:65-120）
 └─ ⑤ 都不行 → enter_safe_mode(cause)：cause = copy_fail_step≠0 ? 0x03 : 0x02
       （0x02=App 区无有效镜像；0x03=备份搬运复核失败）——不会返回
```

**要点**：

- 搬运失败**不会立刻变砖**：旗子保持立着（下次上电重试），流程继续尝试启动 App 区
  现有镜像（旧固件继续跑），App 区也校验不过才进 safe mode；
- 搬运失败的每次尝试都会 `copy_retry_count++` 并持久化，DID 0x2116 可读出；
- Boot 常规路径**没有任何 UDS 服务**，`0x34` 等请求一律静默（运行侧判定见 §20 末尾）。

## 15. 断电恢复与幂等机制

| 断电时点 | 下次上电的结果 |
|----------|----------------|
| 0x36 传输中途 | metadata 还没提交（`backup_valid` 仍是 0，且 0x31 开始时已清过残留旗子）→ Boot 直接启动旧固件；重新走 OTA 即可 |
| 0x37 校验通过、metadata 提交后、复位前 | 旗子已立 → BOOT 下次照常搬运，升级生效 |
| Boot 擦 App 区中途 | 旗子未清（只有复验通过才清）→ App 区校验失败 → 但**搬运会重来**：先验备份区（完好）→ 重新擦写 → 复验 → 提交；备份区数据全程未被破坏 |
| Boot 复制过程中 | 同上：App 区镜像不完整 → `boot_app_image_ok` 失败也无妨，只要旗子在，搬运流程在③就重新执行了完整序列 |
| Boot 复验通过、清旗子后、跳转前 | 旗子已清 + App 区镜像完整 → 下次直接从④跳转，无重复搬运 |

**幂等设计的根**：`backup_valid` 旗子的清除时机 = "复制完成**且**复验通过"（boot_trial.c
boot_copy_backup 第 6 步；文件头注释明确 "flag is cleared only AFTER the copied image
re-verifies in the App region"）。任何中断都落在"旗子还立着"的状态里，重跑无害。

其他幂等点：

- 0x37 重复请求：复位前重发 → `g_trial_ready` 幂等回 `77`（不重复提交）；
  复位后重发 → 落在新 APP 默认会话回 NRC 0x22（预期形态，不判失败）；
- 0x36 重复包：blockSeq 与上次相同时直接重回正响应，不重复写 Flash；
- 0x31 重入：每次执行都先 `ota_dl_abort` 清空下载状态机并清残留旗子，可反复执行。

## 16. OTA 升级脚本用法

脚本：`python_tools/zcanpro_ext_ota_auto.py`（ZCANPRO 扩展脚本，Python 3.8 32 位）。

**两种运行方式**：

1. **ZCANPRO 宿主加载（主用法）**：高级功能 → 扩展脚本 → 打开本文件；
   前提：先打开 CAN 通道（250 kbps，扩展帧）；宿主自动调 `z_main()` 执行完整流程；
2. **命令行指定固件**（standalone 运行时）：

   ```
   python python_tools/zcanpro_ext_ota_auto.py --firmware <bin文件路径>
   ```

   `--firmware` 指定发送的 bin（跳过自动选择），**版本闸门照常执行**；
   无 zcanpro 模块时仅解析参数后退出（参数解析正常的提示会打印）。

**固件选择与版本闸门（fail-closed）**：

| 常量 | 当前值 | 作用 |
|------|--------|------|
| `EXPECTED_SW_VERSION` | `"QC_JYF_FW_1.1.2"` | 升级目标版本。选中 bin 的 strings 里抠不出这个版本串 → **拒闪**（零业务流量退出）；升级后 0xF195 ≠ 此值 → 判定 FAIL。切目标版本只改这一个常量 |
| `BASELINE_SW_VERSION` | `"QC_JYF_FW_1.1.1"` | 升级前基线确认（仅提醒，不拦截） |
| 私钥 | `docs/keys/private.pem` | 打包签名用（脚本按含 docs/keys 的仓库根探测路径） |

- 自动选择路径：扫描 `python_tools/app bin/` 下的 .bin，版本匹配优先、mtime 次序
  （旧版本残留绝不被选中）；
- 载荷前提：用户侧 Keil 把 `can_protocol.c` 的 `SW_VERSION_STR` 改为目标版本后
  **Rebuild**（禁 Incremental Build）→ `pack_image.py` 打包（脚本也会现场补打包）；
  **仓库固件 `SW_VERSION_STR` 保持 `QC_JYF_FW_1.1.1` 零触碰（铁律）**。

**判定闭环（升级成功三条件）**：

1. 复位后 APP 有应答（设备活着）；
2. `0x2113 == 0x00`（单 App 架构恒为 0x00 = App 区运行，仅信息展示）；
3. **`0xF195 == EXPECTED_SW_VERSION`**（Boot 搬运 + 跳转真正生效的铁证）。

**Safe Mode 探测**（升级前探测设备位置）：脚本向 0x18DA0D03 发 `22 2113`，
若收到 `05 62 21 13 FE <fail_step>`（或历史裸帧 `62 21 13 FE <fail_step>`）
→ 设备在 Boot safe mode，抛 SafeModeError（safe mode 不能救砖，需产线整片烧录）；
无应答时先 `3E 80` 唤醒收敛 + 监听 0x18FF260D 生命周期帧再判。

**空片/双无效镜像的恢复**：Boot safe mode 不提供下载服务，**不能通过 CAN 救砖**；
唯一手段 = 产线 `merge_prod_bin.py` 合并镜像从 0x08000000 整片烧录。

# 四、诊断帧（Boot 开机决策链）

## 17. 帧格式总则

| 项 | 值 |
|----|-----|
| CAN ID | `0x18FF480D`（`BOOT_DIAG_CAN_ID`，boot_safe_mode.h） |
| 帧格式 | 29 位扩展帧，DLC=8 |
| 载荷 | `[标记 0xA1~0xA4][数据...]`，不足 8 字节尾部补 `0xCC` |
| 发送方式 | 有界轮询发送：`can_driver_send` 失败立即弃帧；成功才等 `can_driver_wait_tx_idle(3ms)`，总线挂死即弃（boot_safe_mode.c `BOOT_DIAG_TX_TIMEOUT_MS=3`） |
| 设计纪律 | **只报信不改决策**：诊断帧函数不写 metadata、不影响任何选择逻辑；safe mode 既有帧零触碰 |

主机侧抓帧解码配套：`python_tools/zcanpro_boot_diag_capture.py`（与固件同序）。

## 18. M1~M4 诊断帧定义

以 `boot_safe_mode.h` 当前定义为准（字节序 = 线上字节序 = 文档序）：

| 帧 | 标记 | 数据字节 | 发出时机 |
|----|------|----------|----------|
| M1 | `0xA1` | `[b1=metadata 来源: 0=主区 1=备区恢复 2=默认值 0xFF=未记录][b2=magic_ok 0/1][b3=ver_ok 0/1][b4=crc_ok 0/1]` | `boot_metadata_init` 每条加载路径读完 metadata 后 |
| M2 | `0xA2` | `[b1=copy result: 0=流程启动/无待搬运 1=提交成功 0xFF=失败][b2=detail: 失败时=fail_step，无待搬运=0xFF]` | main.c 决策点：无旗子→M2(0,0xFF)；旗子立→M2(0,0)；搬运成功→M2(1,0)；搬运失败→M2(0xFF, copy_fail_step) |
| M3 | `0xA3` | `[b1=pass 0/1][b2=fail_step（0xFF=正在校验）][b3=target: 0=备份区 1=App 区]` | `boot_copy_backup` 两个校验点：验备份区前后、复验 App 区前后（boot_trial.c:136-201） |
| M4 | `0xA4` | `[b1~b4=跳转目标地址，小端 4B]`（正常恒为 `0x08004100`） | `boot_jump_to_app` 内、CAN/SPI 关闭与关中断**之前**（boot_jump.c:77） |

**M2 字节序（OTA-ARCH-0920-D5 统一版）**：`[0xA2][b1=copy result][b2=detail]`——
固件实现、boot_safe_mode.h 注释、主机解码脚本三方同序（boot_safe_mode.c boot_diag_m2
注释；D5 修复前固件曾反着发，已统一，**勿单独改其一**）。

## 19. fail_step 代码表

`g_verify_fail_step`（boot_verify.c）+ 搬运引擎专用码（boot_trial.c）：

| 码 | 含义 | 来源 |
|----|------|------|
| 0x00 | 校验通过 / 未执行校验（无有效 metadata 状态） | boot_verify.c 成功路径 |
| 0x01 | 镜像 magic 不是 "XATO" | boot_verify.c check 1 |
| 0x02 | image_length 为 0 或超出区域范围 | check 2 |
| 0x03 | 载荷 CRC32 校验失败 | check 3 |
| 0x04 | Reset 向量不在运行窗 `[基址+256, 基址+48KB)`（跨区链接的镜像） | check 3b |
| 0x05 | ECDSA 公钥缺失/无效（Device Info 与内置公钥都不可用/内置公钥 magic 被破坏） | check 4 |
| 0x06 | ECDSA P-256 验签失败 | check 4 |
| 0xFD | 搬运：App 区字编程/回读失败 | boot_trial.c copy_program |
| 0xFE | 搬运：App 区擦除失败 | boot_trial.c copy_erase |
| 0xFF | 搬运：metadata.backup_crc32 与镜像头 CRC 不一致（暂存数据与记录对不上） | boot_trial.c boot_copy_backup |

Boot 侧镜像校验 `boot_verify_image`（boot_verify.c）与 APP 侧 `verify_backup_image`
（ota_download.c）校验项一致：magic → 长度 → CRC32 → Reset 向量落运行窗 → 公钥可用 → SHA256+ECDSA。
公钥取值：Device Info（偏移 56，valid 标志偏移 121=0x01 且首字节 0x04）优先，
回落内置公钥（magic `"KEYP"` 完好时）。

## 20. Boot Safe Mode 应答帧

进入条件：开机决策链走到底仍无可启动镜像（`enter_safe_mode(cause)`，cause 0x02=App 区无有效镜像 /
0x03=备份搬运复核失败）。Safe mode 是 `while(1)` 挂起态，**只答探测，不做下载，不能 CAN 救砖**。

| 交互 | 应答（`0x18DA030D`，ISO-TP 单帧，DLC=8，尾部 0xCC 填充） |
|------|------|
| 探测请求 `22 2113`（发到 0x18DA0D03；兼容 ISO-TP SF `03 22 21 13…` 与裸 UDS `22 21 13`） | `05 62 21 13 FE <fail_step> CC CC`（`0xFE`=Boot safe mode 身份标记，区别于 APP 的 0x2113 应答） |
| `3E <sub>`，suppress 位=0 | `02 7E <sub & 0x7F> CC…` |
| `3E 80`（suppress=1） | 不应答 |
| 其他 22 DID | `03 7F 22 11 CC…`（serviceNotSupported） |
| 0x10 / 0x27 / 0x34 等其他服务 | **静默不应答**（无对应分支） |
| 心跳（自发，每 500ms） | `0x18FF260D`：`01 41 42 54 cause fail_step A5 00`（"ABT" 标记帧），同周期重切 SIT1145 Normal |

帧格式出处：boot_safe_mode.c 文件头注释 + `safe_send_sf`/`safe_heartbeat`/`enter_safe_mode`；
与 `zcanpro_ext_ota_auto.py` 头部 SAFE_MODE 注释严格一致（两侧勿改其一）。

**运行侧判定速查**（设备在 APP 还是在 Boot safe mode）：

| 探测结果 | 结论 |
|----------|------|
| 对任意诊断请求有正常应答（正响应或任意 NRC） | 在 APP |
| `22 2113` 应答且 `62 21 13` 后字节为 `0xFE` | 在 Boot safe mode（APP 的 0x2113 恒为 0x00，永远不是 0xFE） |
| 全静默 | 不下结论：先 Standby 唤醒收敛（`3E 80` burst）+ 监听 0x18FF260D 生命周期帧（`01 41 57 4B`=APP 唤醒标识 / `01 41 00`=APP 上电标识 / `01 41 42 54`=Boot safe mode），再判；仍静默 = UNKNOWN，退出取证 |

> 注意：**不能**用"发 0x34 看有没有应答"判 APP/Boot——APP 默认会话对 0x34 回 NRC 0x22，
> Boot safe mode 对 0x34 完全静默，但静默也可能只是收发器没在线，判据必须组合使用。

# 五、DID 详细定义表

全部 DID 的返回实现在 `can_protocol.c` `fill_did_payload`（0x22 读）+ WDBI case 表（0x2E 写）。
标识类 DID 为 **32 字节定长 ASCII，右补空格**（`device_info_pad32` 先全填 0x20 再拷字符串，
device_info.c:40-52）。

## 21. 标识类 DID

| DID | 名称 | 返回格式 | 含义（代码实际行为） |
|-----|------|----------|----------------------|
| 0xF195 | APP 软件版本 | 32B ASCII | `SW_VERSION_STR` 编译常量，当前 `"QC_JYF_FW_1.1.1"`（can_protocol.c:53）。**版本唯一真相源**：不读 metadata、不读镜像头；改版本只改这个常量 |
| 0xF180 | Bootloader 版本 | 32B ASCII | `BOOTLOADER_VER_STR`，当前 `"QC_JYF_BL_1.0.0"`（can_protocol.c:54） |

| 0xF18C | 序列号 SN | 32B ASCII | Device Info 的 `sn`；Device Info 读取失败 → NRC 0x31。产线可写（0x2E，见 §25） |

| 其他任意 DID | — | — | — | 一律 NRC 0x31（不可写） |

# 六、生命周期广播 0x18FF260D

帧格式（lifecycle.c `lifecycle_send`）：`[Byte0=状态码][Byte1=0x41 'A'][Byte2~7=0x00]`；
`0x41` 是 **APP 身份标记**（Boot 的帧用 `0x42 'B'`，如 safe mode 心跳）。

| 状态码 | 名称 | 含义 / 发送时机 |
|--------|------|-----------------|
| 0x01 | BOOTUP | **事件驱动**：首次 CAN 上线后由 `can_protocol_poll` 触发（非上电即时）；bus-off 恢复也会补发（1 秒限频，lifecycle.c lifecycle_on_busoff_recovery）；唤醒场景发扩展标识 `01 41 57 4B <wup计数> <唤醒源> <时长LE2B>`（"AWK" 标记） |
| 0x02 | INITIALIZING | 初始化中 |
| 0x03 | OPERATIONAL | 就绪（BOOTUP 后由 can_protocol_poll 紧接着置位发送） |
| 0x04 | DEGRADED | 降级运行 |
| 0x05 | FAULT | 严重故障 |
| 0x06 | SHUTDOWN | 准备下电/复位（0x37 收尾复位前发送） |

**周期广播禁用**：`lifecycle_is_periodic()` 恒返回 0（lifecycle.c:80-84，
注释 "periodic broadcast disabled"）；`LIFECYCLE_PERIODIC_INTERVAL_MS=1000` 未启用，
固件不周期发送。Boot safe mode 的 500ms ABT 心跳是 Boot 侧独立实现，与此表无关
（帧格式见 §20）。

发送前提：`can_protocol_lifecycle_tx_ready()`——CAN 在线且唤醒后的 quiet 期已过
（quiet 期内 BOOTUP 让位给 UDS 应答）。

## 关键常量

## 中断与时基

Boot 与 APP 各有一份 `at32f422_426_int.c`，结构相同；优先级分组 4（`NVIC_PRIORITY_GROUP_4`）。

| 中断 | 优先级（抢占,子） | 处理 | 出处 |
|------|------------------|------|------|
| SysTick | 内核 | `timer_tick_inc()`，1ms 时基 | at32f422_426_int.c:128 |
| CAN1 RX | (1, 0) | 硬件接收 → 软件 FIFO（16 帧深度）；协议在主循环 `can_driver_poll` 处理 | can_driver.c:203；can_driver.h `CAN_DRIVER_RX_FIFO_SIZE` |
| CAN1 ERR | (2, 0) | 错误标志清除 + bus-off 恢复（恢复回调在主循环跑） | can_driver.c:204 |
| USART2 | (3, 0) | 仅 APP：Qi 芯片 UART 接收 FIFO | qi_uart.c:89 |
| HardFault/MemManage/BusFault/UsageFault | — | 向 `0x20000000` 写 `0xFAUL` 标记后 `NVIC_SystemReset()` | at32f422_426_int.c:55-91 |

Flash 擦写期间（单 Bank）必须屏蔽中断，否则取指与擦写互相卡死——
APP 擦除循环与 Boot 搬运循环都遵循 "IRQ off + flash_unlock → 操作 → flash_lock + IRQ on"
纪律（ota_download.c / boot_trial.c）。

# 八、实现约束与故障速查

## 实现约束

1. **下载全部在 APP 内完成**（0x31/0x34/0x36/0x37）；Boot 常规路径无 UDS。
   设备位置判定按 §20 的正证据组合，不按单一服务有无应答下结论；
2. **镜像必须带 XATO 头**，且 Reset 向量必须指向 App 运行窗 [0x08004100, 0x08010000)
   ——App 区链接的镜像天然满足；其他链接地址的镜像会在 APP 0x37 校验（fail NRC 0x72）
   和 Boot 搬运前校验（fail_step 0x04）两道关被拒；
3. **签名体系**：私钥 `docs/keys/private.pem`，打包时签名进 XATO 头；
   镜像验签公钥优先取 Device Info（可后期更换，写 DID 0x2120 需 Programming+解锁），
   Device Info 未配置时回落 Boot/APP 内置公钥；换内置公钥需重编两个工程；
   0x27 安全解锁验签固定用 APP 编译内置公钥；
4. **0x38 不实现**。签名在镜像头里，0x37 统一校验；
5. **不实现看门狗**。OTA 后确认机制 = metadata 旗子 + BOOT 搬运复验（Boot 侧）；
   metadata 损坏时由双副本+CRC 兜底（主区→备区→默认值重建）；
6. **metadata 掉电安全**：先写备区 0x0801C800 再写主区 0x0801C000；
   旗子清除只发生在搬运复验通过之后；
7. **S3 = 5s**：擦写/多帧传输过程中插 `3E 00`/`3E 80` 保活（任意诊断请求都刷新 S3）；
   宿主脚本长等待期间每 3s 发 `3E 80`；
8. **Device Info（0x0801D000）不在 OTA 擦写范围**：SN/公钥/HW 版本升级后保留；
9. **仓库固件版本铁律**：`SW_VERSION_STR` 保持 `QC_JYF_FW_1.1.1`；
   OTA 目标版本由用户侧 Keil 改常量 + Rebuild 实现，脚本闸门按
   `EXPECTED_SW_VERSION="QC_JYF_FW_1.1.2"` fail-closed 校验。

## 故障速查

| 现象/应答 | 原因与处理 |
|-----------|------------|
| `7F 34 22` | 不在编程会话（S3 掉线或设备已自复位）：重新 `10 02` + `27` 解锁；复位后重试帧落新 APP 默认会话也回 0x22，属预期，按判定闭环核实 |
| `7F 34 24` | 没先 `31 01 FF00` 擦除就发 0x34 |
| `7F 34 31` | 0x34 地址不是 0x08010000，或 size 非法 |
| `7F xx 33` | 没做 0x27 解锁（或解锁态被 S3/会话切换清掉） |
| `7F 27 36/37` | 安全访问失败 3 次锁定：等 30 秒后重新 `27 01` |
| `7F 31 72` | 备份区擦除失败/超时（有界等待耗尽），重试 0x31；反复失败查硬件 |
| `7F 36 73` | blockSeq 不连续，下载作废：重新 0x31 → 0x34 |
| `7F 37 72` | 0x37 收尾失败：字节数不符 / XATO 头坏 / CRC 错 / Reset 向量越窗 / 签名错 / metadata 提交失败。设备未复位、旧固件继续运行，修复载荷后重新升级 |
| 0x37 超时无应答 | 设备可能已回完 77 就自复位（应答丢失）：不判死，等复位后按判定闭环三条件核实 |
| 升级后 0xF195 版本不对 | Boot 搬运没生效或载荷错：抓 Boot 诊断帧 M1~M4 看搬运决策链 + 读 0x2116 重试次数 + 0x2115 启动原因（0x04=搬运失败），按 fail_step 表定位 |
| 设备全静默 | 先 Standby 唤醒收敛（`3E 80` burst）+ 监听 0x18FF260D；Boot safe mode 有 500ms ABT 心跳可辨识；APP/Boot 都无声 = 硬件/总线问题 |
| `22 2113` 回 `…FE <step>` | 设备在 Boot safe mode：App 区无有效镜像。CAN 不能救砖，走产线 `merge_prod_bin.py` 从 0x08000000 整片烧录 |
| 空片/换新 MCU | 同上，整片烧录产线合并镜像（Boot+App），备份区出厂为空 |
