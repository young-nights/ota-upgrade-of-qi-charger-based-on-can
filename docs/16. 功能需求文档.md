# CAN-UDS OTA 功能需求文档

- **版本**: v1.0
- **日期**: 2026-09-04
- **状态**: 正式文档
- **适用范围**: Qi 无线充电模块 CAN-UDS OTA 升级功能

---

## 1. 概述

### 1.1 功能目标

通过 CAN 2.0B 总线（250 kbps，扩展帧），使用 ISO-TP + UDS 协议实现 Qi 无线充电模块的远程固件升级（OTA），支持双槽 A/B 无缝切换，确保升级过程安全可靠。

### 1.2 系统架构

```
CCU（主机）──CAN 250kbps──▶ Qi 充电模块（MCU: AT32F426）
                                  │
                    ┌─────────────┴─────────────┐
                    │       Bootloader 28KB      │
                    │  0x08000000 ~ 0x08006FFF   │
                    │  Safe Mode UDS 下载/验签    │
                    └─────────────┬─────────────┘
                    ┌─────────────┴─────────────┐
                    │     Slot A 42KB | Slot B 42KB     │
                    │  APP 固件（充电业务+UDS 查询）│
                    └─────────────────────────────┘
```

### 1.3 术语定义

| 术语 | 说明 |
|------|------|
| CCU | Central Control Unit，主机控制器 |
| OTA | Over-The-Air，空中升级 |
| UDS | Unified Diagnostic Services (ISO 14229) |
| ISO-TP | ISO 15765-2，CAN 传输层协议 |
| XATO | 自定义镜像头格式（256字节） |
| Trial Boot | 新固件试运行机制 |
| Safe Mode | Bootloader 下载模式 |
| Device Info | 设备信息保留区（0x0801D000） |

## 2. 功能需求

### 2.1 双槽 A/B 升级机制

**需求编号**: OTA-REQ-001

**描述**: 系统支持双槽（Slot A / Slot B）ping-pong 升级模式，运行中的固件不被覆盖，升级始终写入非活跃槽。

**详细要求**:

| 项目 | 说明 |
|------|------|
| Slot A 地址 | `0x08007000`（基址）/ `0x08007100`（入口） |
| Slot B 地址 | `0x08011800`（基址）/ `0x08011900`（入口） |
| 槽大小 | 42KB（0xA800） |
| 镜像头 | 256 字节 XATO 头（magic / length / CRC32 / ECDSA 签名 / 版本 / 时间戳） |
| 活跃槽判断 | 由 metadata `active_slot` 字段决定 |
| 非活跃槽选择 | Bootloader `select_inactive_slot()` 自动选择对面槽 |

**验证标准**:
- 运行 Slot A 时，OTA 写入 Slot B
- 运行 Slot B 时，OTA 写入 Slot A
- 擦写操作不影响正在运行的固件

---

### 2.2 Bootloader Safe Mode 下载

**需求编号**: OTA-REQ-002

**描述**: Bootloader 在特定条件下进入 Safe Mode，通过 UDS 协议完成固件下载全流程。

**进入条件**:
1. metadata `ota_state == DOWNLOADING`（APP 写入标记后复位）
2. 双槽验证均失败（空片、头损坏、验签失败）

**UDS 下载流程（硬门禁顺序）**:

```
10 02          进入编程会话
27 01/03/02    安全访问（ECDSA P-256 签名验证）
2E 2010 01     选择固件类型（APP）
31 01 FF 00    擦除非活跃槽
22 2114        读取目标槽号
34             申请下载
36             传输镜像数据（每包 ≤254 字节）
37             结束传输并验签
11 01          复位进入试运行
```

**关键约束**:
- S3 超时 5 秒，无 UDS 掉回 Default Session
- 擦槽和验签期间返回 NRC 0x78（ResponsePending）
- 未擦槽直接 34 → NRC 0x24
- 未解锁直接擦/写 → NRC 0x33

---

### 2.3 镜像安全校验

**需求编号**: OTA-REQ-003

**描述**: 下载完成后对镜像进行多层安全校验，确保完整性、来源可信和地址合法。

**校验顺序（`boot_verify_image`）**:

| 步骤 | 校验项 | 失败码 |
|------|--------|--------|
| 1 | magic == `0x4F544158`（XATO） | `g_verify_fail_step = 1` |
| 2 | `0 < image_length ≤ 槽大小 - 256` | step = 2 |
| 3 | CRC32(固件数据) == header.crc32 | step = 3 |
| 4 | Reset Handler 落在 `[入口, 槽末)` | step = 4 |
| 5 | ECDSA P-256 签名验证 | step = 5/6 |

**ECDSA 签名方案**:
- 算法: ECDSA P-256（secp256r1）
- 签名格式: 64 字节 IEEE P1363（R‖S，各32字节）
- 公钥来源: 优先 Device Info 区，未配置则回退 Bootloader 内置
- 私钥: `docs/keys/private.pem`（PC 端签名用）

**公钥存储**:
- Device Info 地址: `0x0801D000 + 56`（offset 56）
- 有效标志: `pubkey_valid`（offset 121），`0x01` = 有效
- 写入方式: UDS `2E 2120 [65B公钥]`（需 Programming + SecurityAccess）

---

### 2.4 Trial Boot 试运行机制

**需求编号**: OTA-REQ-004

**描述**: 新固件下载完成后进入试运行状态，必须在规定时间内由 APP 确认，否则自动回滚。

**状态机**:

| 状态 | 转换条件 | 动作 |
|------|----------|------|
| IDLE | 无 | 无 |
| PENDING | 37 成功 | → ACTIVE，retry_count++ |
| ACTIVE | APP 未确认回到 Boot | retry_count++；超限 → 回滚 |
| CONFIRMED | APP 确认 | → IDLE |

**参数**:
- 试运行窗口: 10 秒（APP 端 `ota_trial_poll` 计时）
- 最大重试次数: 3 次
- APP 确认条件: 健康运行 100ms 后调用 `ota_confirm_trial()`
- 回滚操作: `active_slot` 切回旧槽，`trial_state = IDLE`

**关键约束**:
- Trial 期间 `active_slot` 不变（仍指向上一份已确认镜像）
- APP 确认后才更新 `active_slot`
- 回滚后可再次发起 OTA

---

### 2.5 APP 触发 OTA

**需求编号**: OTA-REQ-005

**描述**: APP 通过 UDS 命令触发进入 Bootloader Safe Mode，实现从 APP 发起的远程升级。

**触发流程**:

```
CCU → APP:  10 02（进入编程会话）
CCU → APP:  11 01（hardReset）
APP:        ota_trigger_prepare() → 写 metadata ota_state = DOWNLOADING
APP:        NVIC_SystemReset()
Bootloader: 检测到 DOWNLOADING → 进入 Safe Mode
```

**约束**:
- 非 Programming 会话的 `11 01` 不写 DOWNLOADING，仅复位
- `ota_trigger_prepare()` 不擦槽、不改 `active_slot`
- metadata 写入顺序: 先 Backup 再 Primary（掉电安全）

---

### 2.6 安全访问（SecurityAccess）

**需求编号**: OTA-REQ-006

**描述**: 通过 ECDSA P-256 签名验证实现安全访问控制，防止未授权的固件写入。

**流程**:

```
CCU:  27 01 → 请求 seed（4 字节随机数）
MCU:  67 01 [seed]
CCU:  对 seed 做 SHA256 → 用私钥 ECDSA 签名 → 64 字节
CCU:  27 03 [seq] [4B] × 16 帧（分片传输签名）
CCU:  27 02 → 触发验签
MCU:  SHA256(seed) + uECC_verify(公钥, 签名) → 67 02 或 7F 27 35
```

**安全策略**:
- 连续 3 次验签失败 → 锁定 30 秒（NRC 0x36）
- 锁定期间请求 → NRC 0x37
- 切回 Default Session 不清除失败计数
- APP 和 Bootloader 共用同一套公钥

---

### 2.7 低功耗与 CAN 收发器管理

**需求编号**: OTA-REQ-007

**描述**: 通过 SIT1145 CAN 收发器模式管理实现低功耗控制。

**状态转换**:

| 场景 | SIT1145 模式 | 触发条件 |
|------|-------------|----------|
| 上电默认 | Standby | `sit1145_init()` 末尾 |
| CAN 唤醒 | Normal | RXD(PA11) 拉低 或 CW 标志位 |
| 6 分钟无 UDS | Standby | `can_lp_enter_standby()` |
| Safe Mode 保活 | Normal | 每 500ms 重发 `sit1145_normal_mode_set()` |
| Trial Boot | Normal | `can_protocol_init()` 检测 trial 状态 |

**唤醒检测（双重判断）**:
1. 硬件: RXD(PA11) 拉低
2. 寄存器: `TRANSCEIVER_EVENT` 的 CW 位置位

---

### 2.8 生命周期广播

**需求编号**: OTA-REQ-008

**描述**: APP 运行期间通过 CAN 周期广播状态信息。

| 项目 | 说明 |
|------|------|
| CAN ID | `0x18FF260D` |
| 周期 | 1000ms（1Hz） |
| byte0 | 状态码（BOOTUP=0x01, OPERATIONAL=0x02, SHUTDOWN=0x04） |
| byte1 | `0x41`(APP) / `0x42`(Boot) |

**触发时机**:
- SIT1145 唤醒后: BOOTUP → OPERATIONAL
- CAN Bus-off 恢复后: BOOTUP 广播
- UDS `11 01` 复位前: SHUTDOWN 广播

---

### 2.9 Device Info 设备信息管理

**需求编号**: OTA-REQ-009

**描述**: 在 Flash 保留区存储设备标识信息，OTA 擦槽操作不涉及此区域。

**存储地址**: `0x0801D000`（4KB）

**数据结构（device_info_t v2，512字节）**:

| 字段 | 类型 | 偏移 | 说明 |
|------|------|------|------|
| magic | uint32 | 0x00 | `0x44455649`（DEVI） |
| version | uint32 | 0x04 | 结构版本（当前=2） |
| crc32 | uint32 | 0x08 | CRC32 校验 |
| sn | char[32] | 0x0C | 序列号（ASCII） |
| hw_version | char[8] | 0x2C | 硬件版本 |
| production_date | uint32 | 0x34 | 产线日期 |
| ecdsa_pubkey | uint8[65] | 0x38 | SEC1 未压缩公钥（0x04‖X‖Y） |
| pubkey_valid | uint8 | 0x79 | `0x01`=有效，`0xFF`=未配置 |
| reserved | uint8[390] | 0x7A | 保留 |

**UDS 访问**:
- 读 SN: `22 F18C` → 定长 32 字节
- 写 SN: `2E F18C [32B]`（Programming + 解锁）
- 读公钥: `22 2120` → 65 字节
- 写公钥: `2E 2120 [65B]`（Programming + 解锁）

### 2.10 UDS 服务支持

**需求编号**: OTA-REQ-010

**描述**: APP 和 Bootloader 共同支持的 UDS 服务集。

#### 2.10.1 通用服务（APP + Bootloader）

| SID | 服务 | APP | Boot |
|-----|------|-----|------|
| 0x10 | DiagnosticSessionControl | ✅ | ✅ |
| 0x11 | ECUReset | ✅ | ✅ |
| 0x22 | ReadDataByIdentifier | ✅ | ✅ |
| 0x27 | SecurityAccess | ✅ | ✅ |

| SID | 服务 | 说明 |
|-----|------|------|
| 0x2E | WriteDataByIdentifier | 写固件类型（2010）、SN（F18C）、公钥（2120） |
| 0x31 | RoutineControl | 擦槽（FF00） |
| 0x34 | RequestDownload | 申请下载 |
| 0x36 | TransferData | 传输镜像 |

| SID | 服务 | 说明 |
|-----|------|------|

- 0x31 RoutineControl（擦槽）
- 0x34 RequestDownload

### 2.12 Flash 布局与保护

**需求编号**: OTA-REQ-012

**描述**: Flash 分区布局及 OTA 相关的保护机制。

**布局**:

| 区域 | 起始 | 大小 | 说明 |
|------|------|------|------|
| Bootloader | 0x08000000 | 28KB | 引导/验签/下载 |
| Slot A | 0x08007000 | 42KB | APP 固件 A |
| Slot B | 0x08011800 | 42KB | APP 固件 B |
| Metadata 主 | 0x0801C000 | 2KB | OTA 状态/槽信息 |
| Metadata 备 | 0x0801C800 | 2KB | 掉电安全备份 |
| Device Info | 0x0801D000 | 4KB | SN/公钥/硬件版本 |
| NVM | 0x0801E000 | 8KB | APP 配置 |

**保护机制**:
- Flash 页大小: 1KB（`FLASH_SECTOR_SIZE = 0x400`）
- OTA 擦槽范围: 仅 Slot A/B，不涉及 Device Info 和 NVM
- Device Info 写入: 整页擦除后重写（CRC32 校验）
- Metadata 写入: 先写 Backup 再写 Primary

## 3. 非功能需求

### 3.1 可靠性

- OTA 过程中断电：metadata 先写 Backup 再写 Primary，恢复后可继续或回滚
- Trial 超时：自动回滚到旧固件，不影响设备正常工作
- 双槽无效：自动进入 Safe Mode，可重新下载

### 3.2 安全性

- 固件签名: ECDSA P-256，防止未授权固件写入
- 安全访问: seed + 签名验证，3 次失败锁定 30 秒
- 密钥轮换: 公钥存 Device Info，支持后期通过 UDS 更换

### 3.3 兼容性

- Device Info 版本升级: v1 → v2，CRC 向后兼容（reserved 区全 0xFF）
- 公钥回退: Device Info 未配置时自动回退 Bootloader 内置公钥
- Keil 工程: Slot A `IROM1=0x08007100`，Slot B `IROM1=0x08011900`

### 3.4 性能

- 单帧传输数据: 最大 254 字节（ISO-TP 限制）
- S3 超时: 5 秒
- Trial 窗口: 10 秒
- 生命周期广播: 1 Hz
- SIT1145 保活: 500ms 周期

---

## 4. 约束与限制

1. **下载仅在 Bootloader Safe Mode**，APP 不支持 0x34/0x36/0x37
2. **镜像必须带 XATO 头**，裸 bin 需经 `pack_image.py` 打包
3. **私钥与公钥绑定**，更换密钥需同步更新
4. **不实现看门狗**，试运行超时靠 APP `NVIC_SystemReset()`
5. **S3 = 5 秒**，长操作需插 TesterPresent 保活
6. **Flash 页大小 1KB**，擦除粒度必须匹配

## 控制层面功能需求

### OTA-REQ-015 无线充电控制逻辑

**需求编号**: OTA-REQ-015

**描述**: 通过霍尔传感器（PA0）检测手机放置状态，自动控制5V无线充电供电（PB2），实现智能充电管理。

**引脚定义**:

| 引脚 | 方向 | 功能 | 电平逻辑 |
|------|------|------|----------|
| PA0 | 输入（上拉） | 霍尔传感器 H_OUT | 低电平=有磁场=手机在位；高电平=无磁场=无手机 |
| PB2 | 输出 | 5V 无线充供电使能 | 高电平=使能5V（充电）；低电平=失能5V（停止） |

**控制逻辑**:

| 阶段 | PA0 状态 | PB2 控制 | 说明 |
|------|----------|----------|------|
| 上电初始化 | — | 低电平 | 默认失能5V，g_charge_enabled=false |
| 充电使能+手机在位 | 低电平（有磁场=手机在位） | 高电平 | g_charge_enabled=true 且 PA0 检测到手机 |
| 充电使能+无手机 | 高电平（无磁场=无手机） | 低电平 | 等待手机放置 |
| 充电禁用 | — | 低电平 | g_charge_enabled=false |
| Programming 会话 | — | 低电平 | 进入编程会话时强制失能5V |

**详细要求**:

1. **上电默认**: APP 启动后 `g_charge_enabled=false`，PB2 输出低电平，5V 供电失能
2. **充电使能**: CCU 写 DID `0x2101=0x01` 设置 `g_charge_enabled=true`
3. **霍尔检测轮询**: `board_charge_poll()` 在主循环中调用，周期检测 PA0 电平状态
4. **充电条件**: `g_charge_enabled && PA0 低电平（有磁场 = 手机在位）` → PB2 输出高电平
5. **充电失能**: PA0 高电平（无磁场 = 无手机）→ PB2 输出低电平
6. **编程会话保护**: 进入 UDS Programming Session 时强制失能5V，避免充电干扰 OTA
7. **实时响应**: 霍尔状态变化后应在主循环周期内响应（毫秒级）

**状态转换图**:

```
上电 → g_charge_enabled=false → PB2=LOW（5V失能）
  │
  ├─ CCU 写 0x2101=0x01 → g_charge_enabled=true
  │     └─ PA0=LOW（有磁场=手机在位）→ PB2=HIGH（5V使能，充电中）
  │     └─ PA0=HIGH（无磁场=无手机）→ PB2=LOW（等待手机放置）
  │
  ├─ CCU 写 0x2101=0x00 → g_charge_enabled=false → PB2=LOW
  │
  └─ Programming Session → PB2=LOW（强制失能）
```

**验证标准**:
- 上电后 PB2 为低电平（g_charge_enabled=false）
- CCU 写 0x2101=0x01 使能后，PA0 低电平（手机在位）时 PB2 变为高电平
- PA0 高电平（手机移走）时 PB2 变为低电平
- 进入 Programming Session 后 PB2 强制低电平
- DID 0x2118 可读取当前夹臂状态（PA0 低=0x00 有手机, 高=0x01 无手机）
