## 1. 适用范围

适用于 JYF 向 Lime 交付的**所有 Qi 充电器固件发布**，涵盖开发、验证、正式交付全流程。

## 2. 固件版本要求

### 2.1 版本命名

- MCU1 / MCU2 固件**独立版本管理**，每次发布须明确固件版本
- 格式：`QC_JYF_MCU1_FW_1.1.x`、`QC_JYF_MCU2_FW_1.1.x`
- 初始版本均为 `1.1.1`

### 2.2 文件类型与命名

| 扩展名 | 用途 |
|--------|------|
| `.img` | 应用 OTA 升级固件 |
| `.bin` | 完整 MCU 烧录固件（含 bootloader + 应用），用于直接烧录 |

命名格式：`QC_JYF_MCU1_FW_1.1.x_<MD5>.img` / `.bin`（MCU2 同理）。

硬性规则：
- `<MD5>` 为最终发布文件的**完整 32 字符 MD5**，`.img` 与 `.bin` **各自独立计算**
- 同一版本同时交付 .img 与 .bin 时，两者必须使用**相同的固件版本号**
- 已发布文件**不得在版本号与文件名不变的情况下被修改或替换**
- 任何固件变更都必须给受影响的 MCU 升新版本号

### 2.3 版本递增

- 各 MCU **独立递增**（只改 MCU1 不要求 MCU2 变号）
- Bug-fix、热修等任何变更均需递增

## 3. 硬件版本要求

- 格式：`QC_JYF_HW_1.1.x`，初始 `QC_JYF_HW_1.1.1`
- 影响固件行为/充电功能的硬件变更须升硬件版本号
- 每次固件发布须声明支持的硬件版本，兼容性限制须明确说明

## 4. Release Note 要求

每次发布必须提供，至少包含：MCU1/MCU2 版本、各文件名（含 .img/.bin）、每个文件的完整 32 字符 MD5、发布日期、支持的硬件版本、Git commit ID、Git tag、发布类型、变更内容、已知问题。仅单 MCU 变更时也须写明另一 MCU 的未变版本。

### 4.1 Change Log（每条变更）

问题/需求描述、修改细节、修改后预期行为、受影响 MCU/模块/功能、相关 issue/ticket 号。
**"Bug fix""代码优化""小改动"这类无细节描述不接受。**

### 4.2 Known Issues（已知问题）

发布时全部未解决问题须记录，每条至少含：问题描述、触发条件、影响、可用的规避方法。
影响安全/充电功能/可靠性/固件升级/生产的已知问题须**主动提前通知 Lime**。

## 5. 自测报告要求

必须基于**交付给 Lime 的同一份固件文件**测试（FW OTA 用 .img）。报告至少含：双 MCU 版本、测试文件名、完整 MD5、硬件版本、日期、工程师、环境、结果。两个强制章节：

### 5.1 基础功能回归测试（每次发布必测）

覆盖至少：上电初始化、正常充电启停、Qi 设备检测、充电状态切换、充电功率行为、FOD（如适用）、过压/欠压/过流/过温保护、故障检测与恢复、通信接口、配置读写、双 MCU 版本上报、复位行为、断电重启、异常掉电恢复、长时间连续充电、反复充电循环。

基线回归清单由 Lime 与 JYF 共同商定并长期维护，**强制项不得跳过**。

### 5.2 变更专项测试

Release Note 中**每条变更都必须有对应测试覆盖**：正常场景、边界条件、异常场景、故障恢复、重复操作、上下电、相关功能回归、硬件兼容性。

## 6. 测试用例要求

每条用例至少含：用例 ID、测试项、测试条件、测试步骤、预期结果、实际结果、Pass/Fail。适用时附证据（日志、截图、示波器波形、电压/电流测量、温度等）。所有失败项须明确标出；**强制项失败未经 Lime 明确批准不得正式发布**。

## 7. 固件升级、烧录与回滚测试

- OTA 升级测试用 `.img`；`.bin` 用于直接烧录
- 支持 OTA 的 MCU，量产发布前须验证：旧版→新版 .img 升级、升级后重启、版本号正确、配置与数据保留、升级中断/失败后的恢复（如适用）
- 直接烧录（.bin）须验证：烧录成功、启动成功、版本号正确、基本功能正常
- 支持回滚的还须验证：新→旧回滚、回滚后配置兼容、回滚后基本功能
- 任何升级/烧录/回滚限制须在 Release Note 中写明

## 8. 源码与版本控制

- 每个正式发布的固件文件须**唯一可追溯到源码版本**
- 每个 MCU 版本打 Git tag，推荐格式同版本号（`QC_JYF_MCU1_FW_1.1.x`）
- tag 必须指向生成该固件的**确切源码**；**已发布 tag 不得移动或修改**
- commit ID 与 tag 须记录进 Release Note

## 9. 构建环境要求

保存足以**复现发布固件**的构建信息：编译器/工具链版本、SDK 版本、依赖库版本、构建配置、构建命令/流程、配置文件、所需脚本与工具。
发布文件必须能从对应 Git tag 的源码**重新构建（rebuildable）**。

## 10. 发布包要求

命名：`QC_JYF_MCU1_FW_1.1.x_MCU2_FW_1.1.y_Release.zip`，目录结构：

```
QC_JYF_MCU1_FW_1.1.1_MCU2_FW_1.1.1_Release/
├── Firmware/
│   ├── MCU1/   *.img + *.bin（各带 32 字符 MD5 后缀）
│   └── MCU2/   *.img + *.bin
├── Release_Note/    *_Release_Note.pdf
├── Test_Report/     *_Self_Test_Report.pdf
└── Checksum/        MD5.txt（列出每个发布文件及其完整 MD5）
```

## 11. GitHub Release 要求

每次正式发布须上传到 Lime 指定的 GitHub 仓库并创建 GitHub Release，内容含：双 MCU 版本、日期、变更摘要、Git tag、各 MCU 的 .img/.bin、完整发布包。
**上传文件须与交付给 Lime 的文件完全一致，不得静默替换；任何修改需新版本。**

## 12. 发布通知要求

GitHub Release 完成后须**邮件通知 Lime**，至少含：双 MCU 版本、日期、支持硬件版本、主要变更摘要、已知问题、GitHub Release 链接、每个 .img/.bin 的完整 MD5、特殊验证/部署说明。
**GitHub 上传 + 邮件通知均完成后才算正式交付。**

## 13. 发布前置条件

正式交付前须完成：开发变更完成、代码 review 完成、固件构建成功、.img OTA 升级测试（如适用）、.bin 烧录验证（如适用）、基础回归测试、变更专项测试、Release Note 完成、已知问题记录、每个文件 MD5 校验、Git tag 创建、发布包评审。

## 14. 紧急发布要求

发布后发现严重问题——涉及**安全风险、充电失败、设备损坏风险、过热、保护功能失效、严重可靠性问题、固件升级失败、大规模生产/现场影响**——须及时通知 Lime。
紧急修复仍须遵守全部常规要求：版本递增、Release Note、测试、Git tag、发布包、GitHub Release、邮件通知。

---

## 提炼要点速览（交付 checklist 视角）

1. **双 MCU 独立版本**，初始 1.1.1；任何变更必递增
2. **.img（OTA）/.bin（烧录）** 双文件制，各自独立 32 字符 MD5，同版本一致
3. 发布三件套：**Release Note（含 Change Log 细节）+ 自测报告（基础回归 + 变更专项）+ 发布包**
4. **可追溯闭环**：Git tag（不可动）→ 可重建构建环境 → MD5 → GitHub Release → 邮件通知
5. 强制测试项失败不得发布（除非 Lime 明确批准）；已知问题全部记录
6. 紧急发布免不了任何流程，且严重问题须主动提前通知
