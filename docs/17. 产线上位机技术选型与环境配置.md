## 1. 选型建议：C#（WPF）> Qt

### 1.1 项目约束决定了选型

| 事实 | 对选型的影响 |
|------|----------------|
| 产线工控机几乎必然是 **Windows** | C# 是 Windows 原生一等公民；Qt 在 Windows 上是「跨平台客人」 |
| CAN 盒子是 **ZQWL-CANFD**（`3562:0101`，USB CDC 私有协议，Windows COM7） | C# `SerialPort` 直接开 COM 口即可，零驱动对接成本；本仓库已用 Python 逆出 `49 3B…/5A…A5` 帧格式 |
| 另一套路径是 **ZCANPRO + 扩展脚本**（ZLG USB-CAN） | ZLG 官方 SDK（`zlgcan.dll`）有 C# demo，P/Invoke 很顺 |
| 业务逻辑（UDS / ISO-TP / OTA / SN / SA / Qi IAP）**已全部在 Python 里跑通** | 无论 C# 还是 Qt 都要「重写一遍协议层」，Python 脚本当规格书用即可，选型不因此偏向某一边 |
| 产线场景：大按钮、扫码枪、PASS/FAIL、日志报表、可能接 MES | 这类「表单密集型工装」WinForms/WPF 开发速度远快于 Qt Widgets/QML |
| 团队背景是嵌入式 C + Python + Keil | C# 上手曲线比 Qt（C++/信号槽/qmake/CMake + 部署）平缓得多 |

### 1.2 C# 相对 Qt 的核心优势

1. **部署干净**：`dotnet publish -r win-x64 --self-contained` 出一个目录/单文件，拷到产线机就能跑。Qt 要处理一堆 DLL、插件目录、MSVC 运行库，商业闭源还有 **LGPL 动态链接义务** 或买商业授权。
2. **Windows 生态全开**：串口、条码枪（键盘模拟）、Excel/CSV 报表、SQLite 工装数据库、HTTP 接 MES、多语言资源——全是现成 NuGet。
3. **工业上位机事实标准**：国内汽车电子/消费电子产线工装，C# 占绝对主流，后续交接、招人、找外包都容易。
4. **UI 开发效率**：WPF 的 XAML 做「工位操作界面 + 日志流 + 进度条 + 测试项列表」非常快；Qt 要写到同等观感，工作量大约 1.5～2 倍。

### 1.3 什么时候才选 Qt

- 必须同时跑 Linux/macOS（比如想在 WSL 里直接出 GUI）；
- 团队有强 C++ 维护力量，且要做非常定制的图形界面（波形、3D、实时刷新仪表盘）；
- 需要和固件共享同一套 C 协议栈源码（本仓库是 MCU 裸机工程，共享价值不大）。

**本项目场景三条都不成立。**

### 1.4 不要忽视的第三选项（可作过渡）

如果希望 **一周内就有能用的工装**：Python + **PySide6** 直接包现有 `python_tools/` 逻辑，PyInstaller 打 exe。

代价：杀软误报、Python 运行时体积大、产线 IT 不太喜欢。适合 **研发/试产阶段**，正式量产再换成 C# 也合理——协议逻辑已用 Python 验证过一遍，C# 重写时对照脚本即可。

## 2. 推荐架构（C# 版）

```
QiChargerStationTool (WPF, .NET 8)
├── UI            工位操作 / 扫码 / 测试项列表 / 实时日志 / PASS-FAIL
├── Station       测试流程编排（上电检测→读版本→写SN→OTA→验签→充电启测…）
├── Protocol      UDS + ISO-TP（对照 python_tools/wsl/zcanpro_shim_zqwl.py 重写）
├── Transport     ICanTransport 接口
│   ├── ZqwlSerialTransport   ← 产线默认：COM 口 + 49 3B/5A A5 私有协议
│   └── ZlgCanTransport       ← 可选：zlgcan.dll P/Invoke（若换 ZLG 盒子）
└── Reporting     CSV/Excel + 日志落盘 + 可选 MES 上传
```

协议层以这些脚本为**规格书**（行为已实测对齐）：

| 脚本 | 角色 |
|------|------|
| `python_tools/wsl/zcanpro_shim_zqwl.py` | ISO-TP/UDS 语义（FC、STmin、0x78、suppress） |
| `python_tools/zcanpro/non-qi/zcanpro_ext_ota_auto.py` | OTA 全流程 |
| `python_tools/sn_write_prod.py` | 产线写 SN |
| `python_tools/wsl/zqwl_can_listen.py` | ZQWL 串口协议帧格式 |

**产线不要走 WSL + usbipd。** usbipd 的 attach/detach 在连续生产、多人插拔下很脆；Windows 原生开 COM 口稳定得多。WSL 路径只留给研发调试。

## 3. 环境配置

### 3.1 Windows 侧（上位机开发 + 产线运行）

| 用途 | 安装内容 |
|------|----------|
| IDE | **Visual Studio 2022 Community**（勾选「.NET 桌面开发」）或 JetBrains Rider |
| SDK | **.NET 8 SDK**（LTS）。若产线机是老 Win7/Win10 且不允许装运行时，退到 .NET Framework 4.8 + WinForms |
| CAN 硬件 | ZQWL-CANFD：装厂商 **USB-CDC/VCP 驱动**（或系统自带），设备管理器出现 COM 口（本机实测 COM7）；用串口助手验证 |
| （可选）ZLG | ZLG 官方 USB-CAN 驱动 + `zlgcan.dll` SDK 包，抄官方 C# demo |
| （可选）报表 | NuGet：`ClosedXML`（Excel）、`Serilog`（日志） |
| 固件编译 | Keil MDK + AT32 Device Family Pack（保持现状，Windows 侧编译） |
| 调试器 | AT-Link-Plus 驱动（本机实测 COM4 / usbipd BUSID `3-2`），**只归 Keil**，上位机不要占用 |

**开发自检（Windows PowerShell）：**

```powershell
# 确认 ZQWL 串口
Get-WmiObject Win32_SerialPort | Where-Object {$_.Name -like "*COM*"}
# 或
mode   # 列出 COM 口

# 建工程
dotnet new wpf -n QiChargerStationTool
cd QiChargerStationTool
dotnet add package System.IO.Ports
dotnet run
```

产线机部署：

```powershell
dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true
```

把输出的 exe + 配置（CAN 口、波特率、测试项开关）拷过去即可，无需装 .NET 运行时。

### 3.2 WSL 侧（协议调试 / 跑现有 Python 工具，**非产线必选**）

本仓库 WSL2（Ubuntu-24.04）环境已齐，保持即可：

| 项 | 状态/操作 |
|----|-----------|
| Python | 3.12+ |
| 依赖 | `pip install pyserial` |
| 用户组 | 当前用户需在 `dialout`（本机 `xuanxuan` 已加入，开串口命令无需 `sg dialout` 包裹） |
| USB 盒子进 WSL | Windows 管理员 PowerShell：`usbipd list` → `usbipd bind --busid 3-4` → `usbipd attach --wsl --busid 3-4` |
| 设备节点 | attach 后 `/dev/ttyACM0`，`lsusb \| grep 3562` 确认 |
| 注意 | AT-Link-Plus（BUSID `3-2`）**禁止 attach**，否则 Keil/SWD 掉线；同一盒子同一时刻只能归一边 |

> COM / BUSID 以 `usbipd list` 实测为准，详见根目录 `AGENTS.md`「WSL2 串口 CAN 监听」。仓库旧口径 COM9 / BUSID `7-2` 为其他机器配置。

调试命令（仓库根）：

```bash
# 监听 Boot M1~M4（必须先于 MCU 上电）
python3 python_tools/wsl/zqwl_can_listen.py --port /dev/ttyACM0 \
  --log /tmp/can_boot_listen.log --event /tmp/can_boot_events.log

# 单帧 UDS 探测
python3 python_tools/wsl/zqwl_can_send.py --id 18DA0D03 \
  --data "03 22 F1 95 CC CC CC CC" --wait 2

# 完整 OTA
python3 python_tools/wsl/zqwl_ota_run.py --smoke-read
```

用完 `usbipd detach --busid 3-4` 还给 Windows。

**若希望 C# 上位机在 WSL 里也能跑**（不推荐产线这么干）：WSLg 对 WPF 不友好；要么用 Avalonia（跨平台 .NET UI），要么 UI 留在 Windows、WSL 只跑 headless 协议测试。

### 3.3 产线与研发的职责划分

| 场景 | 跑什么 | CAN 接入方式 |
|------|--------|----------------|
| **产线量产工装** | C# 上位机（单文件 exe） | Windows 原生 COM（ZQWL）或 `zlgcan.dll`（ZLG） |
| **研发协议调试** | 现有 Python 脚本 | WSL + usbipd attach → `/dev/ttyACM0` |
| **试产过渡（可选）** | Python + PySide6 工装 | Windows 原生 COM（同样不要绕 WSL） |

## 4. VS2022 工程与目录搭建（实操）

> 目标：在本仓库内建出可直接用 VS2022 打开、编译、调试、发布的工程骨架，目录结构与第 2 节架构一一对应。

### 4.1 工程放哪：仓库内新增 `QiChargerStationTool/` 目录

产线上位机源码直接放进本仓库，与 `python_tools/`、固件工程平级：

```
ota-upgrade-of-qi-charger-based-on-can/
├── code/
├── docs/                ← 本文档所在
├── python_tools/        ← 协议规格书（C# 重写的对照基准）
├── qi_wireless_bootloader/
├── qi_wireless_code_app/
└── QiChargerStationTool/             ← 新增：产线上位机（C# / VS2022）
```

**为什么放仓库里，而不是单独开仓库/放 Windows 盘：**

1. 协议逻辑要对照 `python_tools/` 里的实测脚本重写（见第 2 节规格书表格），同仓库随手翻、能对拍；
2. 上位机、文档、打包脚本一起打 git tag，产线发布可追溯到同一版本；
3. 符合 AGENTS.md「唯一改动源 = WSL 仓库」约定：改动一律落在 WSL 侧仓库路径。

**VS2022 打开方式（二选一）：**

| 方式 | 做法 | 适用 |
|------|------|------|
| A. 直接开 WSL 路径（推荐起步） | VS2022 → 打开项目/解决方案 → 路径填 `\\wsl.localhost\Ubuntu-24.04\home\whites\embedded_item\ota-upgrade-of-qi-charger-based-on-can\QiChargerStationTool\QiChargerStationTool.sln` | 单一副本，天然符合「WSL 为唯一改动源」；本工程规模小，9p 文件系统够用 |
| B. Windows 本地克隆（编译提速可选） | `git clone` 到 `D:\dev\...` 本地盘开发，改动经 git 同步回 WSL 仓库，**不以 Windows 盘为源** | 若 MSBuild/NuGet 在 `\\wsl.localhost` 上明显变慢再切；否则不必 |

> 方式 A 注意：`obj/`、`bin/`、NuGet 缓存都落在 9p 上，首次还原包会偏慢，属正常现象；杀软实时扫描可把 `QiChargerStationTool/` 加入排除以提速。

### 4.2 解决方案结构（对应第 2 节架构）

一个解决方案、三个项目起步（后续体量大再拆）：

```
QiChargerStationTool/
├── QiChargerStationTool.sln
├── src/
│   ├── QiChargerStationTool.App/          # WPF 表现层（net8.0-windows）
│   │   ├── Views/                         #   工位窗口 / 测试项列表 / 日志面板
│   │   ├── ViewModels/                    #   MVVM（CommunityToolkit.Mvvm）
│   │   ├── Assets/                        #   图标、大按钮样式
│   │   └── appsettings.json               #   COM 口、波特率、测试项开关
│   └── QiChargerStationTool.Core/         # 业务与协议（net8.0，不引用 WPF）
│       ├── Station/                       #   测试流程编排（上电→读版本→写SN→OTA→…）
│       ├── Protocol/                      #   ISO-TP + UDS（对照 zcanpro_shim_zqwl.py）
│       ├── Transport/                     #   ICanTransport + ZqwlSerial / ZlgCan
│       └── Reporting/                     #   CSV/Excel/日志/MES
├── tests/
│   └── QiChargerStationTool.Tests/        # xUnit：协议层单元测试 / 对拍测试
├── config/                                # 产线配置模板（发给工位机的默认配置）
└── README.md                              # 本工具自己的使用说明
```

**分层原则：**

- `Core` 不引用任何 WPF 程序集 → 协议/流程是纯逻辑，`dotnet test` 可直接跑，也方便在 WSL 里跑无界面回归；
- `App` 只做绑定与展示，不写协议字节；
- `Transport` 收在接口 `ICanTransport` 后面，ZQWL/ZLG 可切换（见第 2 节），换盒子不动上层。

### 4.3 VS2022 创建步骤（从零建起）

1. **确认 SDK**：装好 .NET 8 SDK（第 3.1 节），PowerShell 里 `dotnet --list-sdks` 能看到 `8.0.x`。
2. **先建空白解决方案**：在仓库根预先建好空文件夹 `QiChargerStationTool\`，然后 VS2022 → 「创建新项目」→ 搜索模板 **「空白解决方案」**（Blank Solution）→ 解决方案名称 `QiChargerStationTool`，位置选 `...\ota-upgrade-of-qi-charger-based-on-can\QiChargerStationTool` → 确定。建完后解决方案资源管理器显示「解决方案 "QiChargerStationTool"（0 个项目）」。**核对 sln 落点**：应为 `QiChargerStationTool\QiChargerStationTool.sln`（sln 就在 `QiChargerStationTool/` 目录内）；若 VS 在其内又套了一层同名子目录，把 sln 上移一层即可。
   > 为什么不从「WPF 应用」模板起建：那样 VS 会按「解决方案同名目录包项目」的默认布局落盘，sln 不在 `QiChargerStationTool/` 根、项目不在 `src/` 下，与 4.2 节结构对不上，事后要挪文件。先建空白 sln，再逐个添加项目，每一步的落盘位置都可控。
3. **加 WPF 项目**：右键解决方案 → 添加 → 新建项目 → 搜索 **「WPF 应用」**（C#、.NET 8，*不是*「WPF 应用 (.NET Framework)」）→ 项目名 `QiChargerStationTool.App`，**位置改成 `...\QiChargerStationTool\src`** → 创建。VS 会在 `src\` 下生成 `QiChargerStationTool.App\` 子目录。

   **模板辨认对照**（VS 模板列表名字相近，按此表锁定）：

   | 模板列表里的名字 | 选不选 | 说明 |
   |------------------|--------|------|
   | 空白解决方案（Blank Solution） | ✅ 第 2 步用 | 只建 sln，不含任何项目 |
   | **WPF 应用**（C#，.NET） | ✅ 本步用 | 名字**不带**后缀；下一步「框架」下拉选 **.NET 8.0** |
   | WPF 应用 (C#，**.NET Framework**) | ❌ | 老框架，装不了新 NuGet、发不了单文件 |
   | Windows 窗体应用（WinForms） | ❌ | 是 WinForms 不是 WPF，UI 路线不符 |
   | 空项目（Empty Project） | ❌ | 无 XAML/启动骨架，要从零补 |
   | 控制台应用 / Visual Basic 各项 | ❌ | 用途或语言不符 |

   快速筛选：搜索框输入 `WPF` + 语言「C#」+ 平台「Windows」，只剩两个 WPF 模板，选**不带** `(.NET Framework)` 的那个。
4. **加类库与测试项目**（同样右键解决方案 → 添加 → 新建项目，逐个添加）：
   - 「类库」→ `QiChargerStationTool.Core`，位置 `...\QiChargerStationTool\src`
   - 「xUnit 测试项目」→ `QiChargerStationTool.Tests`，位置 `...\QiChargerStationTool\tests`
5. **项目引用**：`App → Core`；`Tests → Core`。（Core 不引用 App，禁止反向引用。）
6. **NuGet 包**（工具 → NuGet 包管理器 → 管理解决方案的程序包）：

   | 包 | 装到 | 用途 |
   |----|------|------|
   | `System.IO.Ports` | Core | ZQWL COM 口收发 |
   | `CommunityToolkit.Mvvm` | App | MVVM 绑定 |
   | `Serilog` + `Serilog.Sinks.File` | App | 实时日志 + 落盘 |
   | `ClosedXML` | Core（Reporting） | Excel 报表 |
   | `xunit` / `Microsoft.NET.Test.Sdk` | Tests | 测试项目模板自带，无需手加 |

7. **设启动项目**：右键 `QiChargerStationTool.App` → 设为启动项目。调试配置用默认的 `Debug | Any CPU` 即可起步——.NET 8 的 AnyCPU 在 64 位 Windows 上默认就跑 64 位，串口不受影响。**锁 `x64` 可选**（只有将来走 ZLG、P/Invoke `zlgcan.dll` 时托管位数才必须与原生 DLL 一致）：菜单 生成 → 配置管理器 → 「活动解决方案平台」下拉 → 新建 → 选 `x64`，「从此处复制设置」选 `Any CPU` → 确定。
8. **F5 验证**：空窗口能起来即骨架完成。

命令行等价（在 `QiChargerStationTool/` 下执行，VS2022 里打开生成的 sln 亦可）：

```powershell
dotnet new sln -n QiChargerStationTool
dotnet new wpf     -n QiChargerStationTool.App   -o src/QiChargerStationTool.App   -f net8.0
dotnet new classlib -n QiChargerStationTool.Core -o src/QiChargerStationTool.Core -f net8.0
dotnet new xunit   -n QiChargerStationTool.Tests -o tests/QiChargerStationTool.Tests -f net8.0
dotnet sln add src/QiChargerStationTool.App src/QiChargerStationTool.Core tests/QiChargerStationTool.Tests
dotnet add src/QiChargerStationTool.App   reference src/QiChargerStationTool.Core
dotnet add tests/QiChargerStationTool.Tests reference src/QiChargerStationTool.Core
dotnet add src/QiChargerStationTool.Core  package System.IO.Ports
dotnet add src/QiChargerStationTool.App   package CommunityToolkit.Mvvm Serilog Serilog.Sinks.File
dotnet add src/QiChargerStationTool.Core  package ClosedXML
```

### 4.6 首次搭环境自检清单

| # | 检查 | 通过标准 |
|---|------|----------|
| 1 | `dotnet --list-sdks` | 有 `8.0.x` |

| 4 | 装好 ZQWL 驱动后 `mode` | 出现 COM7（以实测为准） |
| 5 | 在 Core 里 `SerialPort.GetPortNames()` | 能枚举到 COM 口（临时按钮或单测验证） |
| 6 | `dotnet test` | xUnit 默认用例全绿 |

全部通过后，即可按第 5 节开始把 `zcanpro_shim_zqwl.py` 的 ISO-TP/UDS 语义搬进 `Core/Protocol`。

---

## 5. 建议落地路径

1. **先定传输层**：产线用 ZQWL COM 口还是 ZLG 盒子？定了就能锁 `ICanTransport` 的默认实现。
2. **C# 重写协议层**：对照 `zcanpro_shim_zqwl.py` 把 ISO-TP + UDS（含 0x78、suppress、FC/STmin）搬过来，用现有 Python 脚本做对拍。
3. **按工位编排测试项**：上电识别 → 读版本 `0xF195` → 写 SN `0xF18C` → OTA → 验签 → 充电启停 → Qi 状态，做成可勾选的测试序列 + 统一 PASS/FAIL 报表。
4. **试产阶段**可并行保留 Python 工具做回归，量产工装只发 C# 单文件。

---

## 6. 一句话总结

产线 Windows 工装选 **C# / WPF**，CAN 直连 COM（ZQWL）或 ZLG SDK；WSL 只做协议调试（usbipd + 现有 Python），不进产线。Qt 在本项目约束下没有收益，只有部署和授权成本。
